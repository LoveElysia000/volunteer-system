# Product Completeness 4-Week Roadmap

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在 4 周内把系统从“可用”推进到“相对完整且可运营”，优先补齐运营闭环能力。

**Architecture:** 保持现有分层架构（`router -> handler -> service -> repository`），优先做增量扩展。先完成 P0 的审核效率、导入能力、自动收口与运营看板，再做 P1 的证书和通知增强，P2 特性后置。

**Tech Stack:** Go, Hertz, GORM, MySQL, Redis(可选), Protobuf/OpenAPI, Go test

## 3. 任务清单（实现思路 + 大致方法）

### Task A: 审核中心升级（P0）

**实现思路**
统一审核入口，减少多页面切换，提升处理吞吐。

**大致方法**
1. 扩展待审查询：支持多目标类型、关键词、时间区间、SLA 标记。
2. 扩展批量审批：返回 `successCount` + `failedIds` 的部分成功结构。
3. 做权限收敛：按组织作用域和 RBAC 权限校验。
4. 补索引：围绕 `target_type/status/created_at` 和常用组合筛选建立索引。

**验收标准**
1. 管理员可在同一列表处理多个审核目标。
2. 批量审批可用且失败项可追踪。
3. 权限越界请求被稳定拒绝。

**风险与依赖**
1. 审核状态与业务状态映射容易出错。
2. 依赖审核快照解析一致性和历史数据兼容。

### Task B: 导入中心（P0）

**实现思路**
将“同步重接口”改为“异步任务流”，保障稳定性和可追踪性。

**大致方法**
1. 新增任务模型：`import_tasks`、`import_task_details`。
2. 接口分层：上传创建任务、任务状态查询、失败回执查询。
3. Worker 异步处理：解析文件 -> 逐行校验 -> 批量写库 -> 记录失败详情。
4. 保证幂等：基于任务ID/业务唯一键防重放。

**验收标准**
1. 支持志愿者、活动两类导入。
2. 失败行可查看并带明确原因。
3. 大文件导入不会阻塞主请求链路。

**风险与依赖**
1. 数据质量波动会放大失败率。
2. 需要统一字段映射与模板版本。

### Task C: 活动自动归档/自动收口（P0）

**实现思路**
用系统任务替代人工收口，确保活动状态长期准确。

**大致方法**
1. 增加定时任务调度（建议每小时）。
2. 按条件批量更新：过期且处于可招募态的活动转为已结束。
3. 保证幂等更新：重复执行不产生副作用。
4. 加观测日志：每次执行记录处理数量和耗时。

**验收标准**
1. 过期活动在预期时间窗内自动收口。
2. 重复运行不会产生状态抖动。
3. 异常可通过日志和指标定位。

**风险与依赖**
1. 时间边界处理（时区、夏令时）需统一。
2. 批量更新范围需避免误伤。

### Task D: 运营看板 V1（P0）

**实现思路**
先做可决策的最小指标集，不追求一次性全量 BI。

**大致方法**
1. 指标范围：报名转化、出勤率、工时发放量。
2. 查询维度：组织、时间区间。
3. 后端聚合：统一统计口径，避免前端拼算。
4. 权限控制：仅具备分析权限的角色可访问。

**验收标准**
1. 可按组织/时间稳定查询核心指标。
2. 指标口径文档化且与业务定义一致。
3. 查询性能满足常规运营使用。

**风险与依赖**
1. 历史数据缺失导致指标偏差。
2. 口径不统一会影响业务信任。

### Task E: 端到端回归与稳定性基线（P0）

**实现思路**
将关键业务链路固化成自动化用例，确保迭代不破坏核心流程。

**大致方法**
1. 编排主链路回归集：成功路径 + 权限拒绝路径。
2. 发版前固定执行：`go test ./...` + 关键接口 smoke。
3. 将发布检查清单纳入常规流程并留存结果。

**验收标准**
1. 核心链路回归可一键执行。
2. 发版前检查可复现、可追溯。

**风险与依赖**
1. 测试环境与生产口径不一致会导致误判。

### Task F: 证书系统（P1）

**实现思路**
补齐“服务结果交付”能力，提升平台完整性。

**大致方法**
1. 新增模板管理与证书实例模型。
2. 按活动或志愿者范围批量生成证书。
3. 提供下载接口与操作审计。

**验收标准**
1. 模板创建/更新/启用可用。
2. 证书生成与下载链路可闭环。

**风险与依赖**
1. 模板渲染与文件生成的性能与一致性风险。

### Task G: 通知中心增强（P1）

**实现思路**
从基础消息能力升级到可运营、可筛查的消息中心。

**大致方法**
1. 增加筛选维度：未读、业务类型、时间范围。
2. 增加统计能力：未读总数、分类计数。
3. 增加业务跳转线索：`bizType + bizId` 追踪。

**验收标准**
1. 通知列表可筛选与分页。
2. 未读统计准确且性能稳定。

**风险与依赖**
1. 高并发下未读计数一致性挑战。

### Task H: 活动推荐（P2）

**实现思路**
先规则推荐，后模型推荐，降低前期复杂度。

**大致方法**
1. 规则打分：历史参与、时间匹配、组织偏好、地理因子。
2. 返回推荐原因字段，提升可解释性。
3. 后续预留模型排序扩展点。

**验收标准**
1. 推荐接口稳定可用。
2. 有基础转化提升数据可观测。

**风险与依赖**
1. 冷启动用户推荐效果偏弱。

### Task I: 高级 AI 场景扩展（P2）

**实现思路**
围绕运营提效场景做工具化，不改变主业务闭环。

**大致方法**
1. 增加运营助手场景：报表解读、活动文案建议、FAQ。
2. 工具调用全链路审计与权限边界控制。

**验收标准**
1. 新场景可用且不越权。
2. AI 失败不影响核心业务请求。

**风险与依赖**
1. 提示词与工具编排质量直接影响可用性。
